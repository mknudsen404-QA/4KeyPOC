# Wrong-firmware recovery + silent-failure hardening plan

Written 2026-09-14. Handoff document for an implementing agent. Read the
whole thing before touching anything; Phase 1 involves flashing real
hardware and needs the human at the keyboard.

## Incident summary

The NeoKey board was plugged into a second Mac (no bridge installed).
Observed: board has power, macOS mounted a USB drive and showed the
"Allow accessory to connect?" prompt, keys do nothing and never light.

**Root cause (confirmed from build artifacts, pending laptop
confirmation):** the board is running `firmware/msc_cdc_spike`, not
`firmware/neokey`. Evidence:

- Every `neokey` build in `~/Library/Caches/arduino/sketches/*/build.options.json`
  used `esp32:esp32:esp32s3:CDCOnBoot=cdc` → USB Mode = Hardware CDC/JTAG.
  That mode has no mass-storage class; it *cannot* mount a drive.
- The only build that can mount a drive is the spike:
  `esp32:esp32:esp32s3:USBMode=default,CDCOnBoot=cdc,FlashSize=16M,PartitionScheme=app3M_fat9M_16MB`.
- The spike deliberately contains no NeoKey/seesaw code
  (`firmware/msc_cdc_spike/msc_cdc_spike.ino` header comment), so dark,
  unresponsive keys with a power LED is its *expected* behaviour.
- `docs/design/plug-and-play-installer-plan.md` "Spike findings" says the
  spike was flashed onto the one working board on 2026-09-12 and reflashed
  back afterward. A `neokey.ino.bin` exists from 2026-09-13 21:03, but
  `firmware/neokey/test/compile.sh` is compile-only and produces an
  identical artifact, and the spike README documents that native-USB
  uploads frequently fail with "No serial data received". The reflash-back
  most likely never landed.

Two contributing weaknesses, fixed in Phases 3–4:

- `firmware/neokey/neokey.ino` `setup()` spins in `while (!ok)` forever with
  zero serial or LED output if the seesaw does not answer. A hung NeoKey
  chip (documented quirk: needs a full power cycle after heavy
  flash/reset cycling) is indistinguishable from wrong firmware or a dead
  board.
- Nothing on the spike identifies itself as "not the real firmware" to a
  user looking at the board, and `switchboard doctor` cannot tell the
  difference either.

Also note for anyone verifying on a Mac **without** the bridge: with the
correct firmware, keys A/B/C render `Status::Empty` = `0x000000`
(`firmware/neokey/status_table.h`) until the bridge sends `agent.update`.
Only the ~0.6 s white boot sweep (2 s after power-up) and key D glowing
magenta while held are visible locally. That is not a fault.

## Ground rules for the implementer

- **Never flash the board without the human explicitly saying "flash it
  now" in that turn.** Compile freely; upload only on sign-off.
- Do not hand-edit `firmware/neokey/status_table.h`; it is generated by
  `python3 -m switchboard.status_table --emit-header` (run from `host/`).
  This plan does not require changing it.
- Do not change key mapping, LED rendering, the JSON protocol shape, or
  the seesaw no-reset workaround in `neokey.ino`. Phase 3 only *adds*
  diagnostics.
- Keep `msc_cdc_spike` standalone (no NeoKey/seesaw includes) — that is a
  stated design constraint in its header.
- All host changes need tests under `host/tests/` and must pass
  `python -m pytest host/tests -q -m "not hardware"`. Firmware changes
  must pass `firmware/neokey/test/run.sh` and `firmware/neokey/test/compile.sh`.
  CI (`.github/workflows/ci.yml`) runs both.
- Commit per phase with a message prefixed `Recovery N.x:` so the history
  reads like the existing `Phase N.x:` commits.

## Phase 0 — Confirm the diagnosis on the laptop (human, 2 min)

Run on the laptop with the board plugged in and paste results into the
session:

```sh
ls /Volumes/; diskutil list external
system_profiler SPUSBDataType | grep -A12 -i "espressif\|switchbd\|usb jtag"
ls /dev/cu.*
screen /dev/cu.usbmodemXXXX 115200      # quit: Ctrl-A, K, Y
```

Decision table:

| Observation | Meaning | Next |
|---|---|---|
| `SWITCHBD` volume present, or USB product string contains "Installer"/"Espressif Device", or serial shows `CDC alive, MSC volume mounted alongside it` every 2 s | Spike firmware on board | Phase 1 |
| Product string "USB JTAG/serial debug unit", no volume, serial silent even when pressing keys | NeoKey firmware on board but seesaw init hung | Full power cycle (unplug 5 s). If still dead, Phase 1 anyway, then Phase 3 makes this visible in future |
| Product string "USB JTAG/serial debug unit", serial prints `{"event":"agent.select",...}` on key press | Firmware is fine; laptop just has no bridge | Skip to Phase 5 |

If the human already double-clicked `Install Switchboard.command` on the
laptop, also collect `~/Library/Logs/Switchboard/installer.log` from the
laptop.

Do not block on Phase 0: Phases 3 and 4 are pure code and can be done
first while waiting.

## Phase 1 — Reflash `firmware/neokey` on the dev Mac

Prereqs on the dev Mac (already present): `arduino-cli` at
`/opt/homebrew/bin/arduino-cli`, esp32 core 3.3.11, "Adafruit seesaw
Library", ArduinoJson v7.

1.1 Compile (safe, no hardware):

```sh
cd ~/Documents/Codex-Micro-Matt/Codex_Micro_Display
arduino-cli compile --fqbn esp32:esp32:esp32s3:CDCOnBoot=cdc --warnings default firmware/neokey
```

Expected: success, sketch ~340 KB. If Phase 3 has landed first, compile
that version — it is the one that should go on the board.

1.2 Plug the board into the dev Mac, find the port: `ls /dev/cu.usbmodem*`.

1.3 Get explicit sign-off, then upload:

```sh
arduino-cli upload --fqbn esp32:esp32:esp32s3:CDCOnBoot=cdc -p /dev/cu.usbmodemXXXX firmware/neokey
```

Because the board is currently in TinyUSB (OTG) mode, auto-reset into the
bootloader is likely to fail with "No serial data received". Fallback
(documented in `firmware/msc_cdc_spike/README.md`): hold BOOT, tap RESET,
release BOOT, re-run `ls /dev/cu.usbmodem*` (the port name usually changes
— bootloader mode has no CDC), and upload to the new port.

Partition scheme note: the spike used `app3M_fat9M_16MB`; `neokey` uses
the core default. `arduino-cli upload` rewrites the partition table, so
this is fine and matches how the board worked before. Do not "fix" the
flash size as part of this recovery.

1.4 **Full power cycle** afterward (unplug, wait 5 s, replug) so the seesaw
chip comes up clean — the documented quirk.

Acceptance: upload reports success and `ls /Volumes/` shows no `SWITCHBD`.

## Phase 3 — Make `neokey.ino` fail loudly

Files: `firmware/neokey/neokey.ino`, `firmware/neokey/README.md`,
`host/switchboard/reducer.py`, `host/switchboard/doctor.py` (optional),
`host/tests/test_reducer.py`, `host/README_BRIDGE.md` ("Current firmware
events" section).

The seesaw hosts the LEDs, so when it is unresponsive there is nothing
to blink — serial is the only channel. Design:

3.1 Add a firmware identity constant near the top of the sketch:

```cpp
#define FIRMWARE_NAME "neokey"
#define FIRMWARE_BUILD __DATE__ " " __TIME__
```

3.2 Add `sendBootEvent(const char *stage, int attempt)` (or extend
`sendEvent`) emitting one JSON line per call. Required lines:

- Immediately after `Serial.begin`/`delay(2000)` and before I²C:
  `{"event":"boot","stage":"start","firmware":"neokey","build":"<FIRMWARE_BUILD>"}`
- Inside the `while (!ok)` retry loop, each failed attempt:
  `{"event":"error","reason":"seesaw_no_response","attempt":N}`
  Keep retrying forever (the device is useless without the seesaw) but
  make the retry delay 1000 ms as today, so the line rate is ~1/s.
- After the startup sweep completes:
  `{"event":"boot","stage":"ready","firmware":"neokey","attempts":N}`

Keep `StaticJsonDocument<128>`-style sizing consistent with `sendEvent`;
`build` is ~20 chars, so 192 is enough for the boot line.

3.3 Host: in `host/switchboard/reducer.py::_reduce_board_event`, handle
`boot` and `error` explicitly (before the fallthrough) so they log as
`Log("Board boot: <stage> firmware=<name> build=<build>")` and
`Log("Board error: seesaw_no_response (attempt N) — power-cycle the board")`.
Do not mutate slot state on either. Add reducer tests for both, plus a
golden-trace entry if `host/tests/test_golden.py` conventions make that
cheap.

3.4 Optional but recommended: `doctor.check_serial_port` currently only
proves the port opens. If it already reads a line or two, extend it to
report "firmware: neokey (build …)" when a `boot` line is seen and
"board is retrying seesaw init — power-cycle it" when an `error` line is
seen. If it does not read lines today, leave this for Phase 4.2 which
adds a firmware-identity check.

3.5 Docs: add `boot` and `error` to "Current firmware events" in
`host/README_BRIDGE.md`, and add a "What you should see on the serial
port at boot" paragraph to `firmware/neokey/README.md`.

Acceptance: `firmware/neokey/test/run.sh` and `test/compile.sh` pass
(led_model.h untouched), host tests pass, and after Phase 1 the `boot`
lines are visible in `screen`.

## Phase 4 — Make the spike unmistakable

Files: `firmware/msc_cdc_spike/msc_cdc_spike.ino`,
`firmware/msc_cdc_spike/README.md`, `host/switchboard/doctor.py`,
`host/tests/test_doctor.py`.

Do **not** rename the `SWITCHBD` volume label in `gen_fat.py`: the spike
is the seed for the shipped installer and the label is part of what it
validates.

4.1 Firmware: make the serial ping self-identifying and JSON-shaped so
the bridge can parse it instead of ignoring it as log text:

```cpp
Serial.println("{\"event\":\"boot\",\"stage\":\"ping\",\"firmware\":\"msc_cdc_spike\",\"build\":\"" __DATE__ " " __TIME__ "\"}");
```

Keep the 2 s cadence. Also set `MSC.productRevision("spike")` so
`system_profiler SPUSBDataType` shows it. Update the spike README's
"What to check once flashed" and add a "If your keys are dead and a
SWITCHBD drive appears, you are on this spike — reflash
`firmware/neokey`" note.

4.2 Host: add `doctor.check_firmware_identity(port)`:

- If `/Volumes/SWITCHBD` exists **or** the first `boot` line read from
  the port has `firmware != "neokey"` → FAIL with
  "Board is running <firmware> — reflash firmware/neokey (see
  docs/design/wrong-firmware-recovery-plan.md)".
- If a `boot` line with `firmware == "neokey"` is seen → OK, include
  build string.
- If the port opens but nothing arrives within ~3 s → WARN "no boot line
  seen; board may be mid-boot or running pre-2026-09-14 firmware".
  (Boot lines are only emitted at power-up, so a board already running
  will be silent — the check must not be a hard FAIL on silence.)

Wire it into `run_checks` and cover all three outcomes in
`host/tests/test_doctor.py` using the existing fake-port patterns there.
Skip the check cleanly when no port is given, like `check_serial_port`.

4.3 Bridge runtime: when the bridge's reader sees a `boot` with
`firmware != "neokey"`, log one loud line and keep running (it should not
crash or exit). Add a reducer test.

Acceptance: host tests pass; spike compiles with
`arduino-cli compile --fqbn esp32:esp32:esp32s3:USBMode=default,CDCOnBoot=cdc firmware/msc_cdc_spike`
(compile only — do not flash the spike to the working board).

## Phase 5 — Laptop bring-up

Only after Phases 1–2 pass on the dev Mac.

5.1 Bridge install on the laptop, either route:

- Installer route (exercises the product flow): if the laptop still has
  the spike volume mounted from before, do **not** use it — the board
  will be reflashed by then. Instead clone the repo and run
  `host/setup.sh`, exactly what `Install Switchboard.command` does.
- Manual route: `git clone <repo> ~/4KeyPOC && cd ~/4KeyPOC/host && ./setup.sh`.

5.2 On the laptop: `switchboard doctor` (all checks green except those
that legitimately need first-run permissions — Terminal automation /
Accessibility prompts will appear; grant them).

5.3 Plug in the board: expect boot sweep, `boot` event in the bridge
log (`~/Library/Logs/Switchboard/bridge.out.log`), then key A selects
slot 1 and the bridge launches/attaches per `agents.json`. Keys light
with status colours only once agents are registered — this is the
correct behaviour, per the note in the summary.

5.4 Record any laptop-specific friction (permission prompts, port
naming) in `host/README_BRIDGE.md` → "Setting up on a new Mac".

Acceptance: board works on the laptop end-to-end; `bridge.out.log` no
longer shows `No USB serial port found` while the board is plugged in.

## Suggested order

3 → 4 (pure code, testable without hardware) → 1 → 2 → 5. Phase 0 can
happen any time the human has the laptop handy. Ship 3 and 4 before
flashing so the board that goes on the laptop already self-identifies.

## Out of scope

- Switching `neokey` to a 16 MB partition scheme.
- The MSC "advertise forever vs. stop after handshake" question.
- Any change to status colours, the busy ramp, or key semantics.
